یک ایجنت هوش مصنوعی بدون دسترسی به اطلاعات و ابزارهای واقعی سازمان، بیشتر شبیه یک مشاور باهوش اما منزوی است. می‌تواند پیشنهاد بدهد، اما برای خواندن وضعیت سفارش، یافتن سند، به‌روزرسانی CRM یا ساخت گزارش باید به سیستم‌های بیرونی متصل شود. تا مدت‌ها هر اتصال با کد و قرارداد اختصاصی ساخته می‌شد؛ روشی که با افزایش تعداد مدل‌ها، ابزارها و ایجنت‌ها به‌سرعت پرهزینه و شکننده می‌شود.

**پروتکل MCP** یا **Model Context Protocol** برای استانداردکردن همین ارتباط شکل گرفته است. MCP یک قرارداد باز میان برنامه هوش مصنوعی و منابع داده یا ابزارها ایجاد می‌کند؛ به‌طوری‌که ایجنت بتواند قابلیت‌های در دسترس را بشناسد، داده لازم را دریافت کند و در صورت مجازبودن عملی انجام دهد.

در این راهنما، MCP را از نگاه مدیران فناوری، محصول، داده و امنیت بررسی می‌کنیم: معماری آن چیست، چه تفاوتی با API دارد، کجا ارزش می‌سازد و برای استقرار امن آن چه کنترل‌هایی لازم است.

## MCP چیست؟

Model Context Protocol یک استاندارد باز برای ارائه «زمینه» و «ابزار» به مدل‌های زبانی و ایجنت‌های هوش مصنوعی است. Anthropic هنگام معرفی MCP در نوامبر ۲۰۲۴، هدف آن را جایگزین‌کردن اتصال‌های پراکنده و اختصاصی با یک روش مشترک برای ارتباط سامانه‌های هوش مصنوعی با منابع داده و ابزارهای کاری توضیح داد.

تشبیه رایج، MCP را شبیه USB-C برای برنامه‌های هوش مصنوعی می‌داند: USB-C همه دستگاه‌ها را یکسان نمی‌کند، بلکه قرارداد اتصال را استاندارد می‌کند. MCP نیز CRM، پایگاه داده، سامانه اتوماسیون یا سرویس ابری را یکی نمی‌کند؛ فقط روش معرفی قابلیت‌ها و تبادل درخواست و پاسخ را هماهنگ می‌سازد.

این استاندارد امروز صرفاً یک پروژه وابسته به یک مدل خاص نیست. MCP به یک اکوسیستم باز تبدیل شده و ابزارها و SDKهای متعددی از آن پشتیبانی می‌کنند. بااین‌حال «باز بودن استاندارد» به معنی امن‌بودن خودکار هر سرور یا اتصال نیست؛ اعتبار و سطح دسترسی هر جزء باید جداگانه ارزیابی شود.

## چرا ایجنت‌های سازمانی به یک پروتکل مشترک نیاز دارند؟

فرض کنید یک ایجنت تدارکات باید موجودی را از ERP بخواند، قرارداد را در سامانه اسناد پیدا کند، قیمت تأمین‌کنندگان را مقایسه کند و پیش‌نویس درخواست خرید بسازد. در روش سنتی، برای هر ترکیب «برنامه هوش مصنوعی × سامانه سازمانی» یک اتصال اختصاصی لازم است.

اگر پنج دستیار و ده سامانه داشته باشیم، تعداد اتصال‌ها و هزینه نگهداری به‌سرعت رشد می‌کند. تغییر API، فرمت داده، روش احراز هویت یا مدل نیز ممکن است چندین اتصال را هم‌زمان بشکند. MCP یک لایه مشترک می‌سازد تا:

• قابلیت‌های هر سامانه با ساختاری قابل کشف معرفی شوند؛

• یک ابزار سازمانی برای چند میزبان و ایجنت قابل استفاده باشد؛

• سیاست‌های دسترسی، ثبت رخداد و تأیید انسانی در یک مرز مشخص اعمال شوند؛

• تغییر مدل یا رابط کاربری الزاماً به بازنویسی همه اتصال‌ها منجر نشود.

ارزش واقعی MCP کاهش چند خط کد نیست؛ ارزش آن ایجاد معماری قابل توسعه و قابل حاکمیت برای مجموعه‌ای از ایجنت‌ها و ابزارهاست.

## معماری MCP چگونه کار می‌کند؟

مستندات رسمی MCP معماری را به سه نقش اصلی تقسیم می‌کند:

### ۱. میزبان یا Host

Host همان برنامه‌ای است که کاربر در آن با هوش مصنوعی تعامل دارد؛ مانند یک دستیار سازمانی، محیط توسعه یا سامانه تحلیل. میزبان چرخه اجرای ایجنت، سیاست‌های امنیتی، رضایت کاربر و نحوه ارائه ابزارها به مدل را مدیریت می‌کند.

### ۲. کلاینت MCP

کلاینت داخل میزبان قرار می‌گیرد و با یک سرور MCP ارتباط برقرار می‌کند. در معماری مرجع، هر کلاینت اتصال مشخصی با یک سرور دارد. این تفکیک کمک می‌کند مرز میان سرورها روشن بماند و هر سرور فقط اطلاعات لازم را دریافت کند.

### ۳. سرور MCP

سرور، قابلیت‌های یک سیستم یا دامنه را با قرارداد MCP ارائه می‌کند. برای نمونه، یک سرور می‌تواند ابزارهای CRM را در اختیار ایجنت بگذارد و سروری دیگر فقط دسترسی خواندن به اسناد سیاستی داشته باشد.

سرورها معمولاً سه نوع قابلیت ارائه می‌کنند:

• **Tools:** عملیات قابل اجرا، مانند جست‌وجوی مشتری، ایجاد تیکت یا تولید گزارش؛

• **Resources:** داده و محتوای زمینه‌ای، مانند فایل، رکورد، تاریخچه Git یا سند؛

• **Prompts:** قالب‌های ازپیش‌تعریف‌شده برای اجرای یک جریان کاری مشخص.

مدل ممکن است از توضیح ابزارها تصمیم بگیرد کدام Tool را فراخوانی کند؛ به همین دلیل نام‌گذاری، شرح دقیق ورودی و خروجی و محدودیت هر ابزار فقط موضوع تجربه توسعه‌دهنده نیست، بلکه بخشی از ایمنی سیستم است.

## یک مثال عملی از MCP در سازمان

درخواست کاربر را در نظر بگیرید: «وضعیت سه فرصت فروش بزرگ این ماه را بررسی کن و برای موارد متوقف‌شده یک برنامه پیگیری پیشنهاد بده.»

جریان مناسب می‌تواند چنین باشد:

1. میزبان هویت کاربر و محدوده مجاز او را مشخص می‌کند.
2. ایجنت از طریق سرور MCP مربوط به CRM، ابزار جست‌وجوی فرصت‌ها را می‌بیند.
3. فقط رکوردهایی که کاربر مجاز به مشاهده آن‌هاست بازگردانده می‌شوند.
4. ایجنت داده‌ها را تحلیل و پیشنهاد پیگیری را آماده می‌کند.
5. اگر کاربر بخواهد وظیفه‌ای در CRM ثبت شود، سیستم قبل از عملیات نوشتنی تأیید می‌گیرد.
6. ورودی، ابزار انتخاب‌شده، نتیجه و هویت درخواست‌کننده در گزارش ممیزی ثبت می‌شوند.

در این سناریو، MCP مسیر ارتباط را استاندارد می‌کند؛ اما تصمیم درباره مجوز، تأیید، محدودیت داده و ثبت رخداد همچنان مسئولیت معماری سازمان است.

## تفاوت MCP و API چیست؟

MCP جایگزین API نیست. بسیاری از سرورهای MCP در پشت صحنه از APIهای موجود استفاده می‌کنند. تفاوت اصلی در سطح انتزاع و مخاطب قرارداد است.

API معمولاً برای فراخوانی مستقیم توسط نرم‌افزار و توسعه‌دهنده طراحی می‌شود. MCP علاوه بر انتقال درخواست، قابلیت‌ها را به شکلی معرفی می‌کند که میزبان هوش مصنوعی و مدل بتوانند آن‌ها را کشف و استفاده کنند. توضیح ابزار، طرح ورودی، نوع خروجی و سازوکار مذاکره قابلیت‌ها بخشی از این قرارداد هستند.

به زبان ساده:

• API راه دسترسی برنامه‌نویسی به یک سرویس است؛

• MCP یک لایه استاندارد برای ارائه همان سرویس‌ها به برنامه‌ها و ایجنت‌های هوش مصنوعی است؛

• سرور MCP می‌تواند یک یا چند API، پایگاه داده یا سیستم داخلی را پشت یک مرز کنترل‌شده قرار دهد.

اگر APIهای سازمان نامنظم یا بدون کنترل دسترسی باشند، افزودن MCP مشکل بنیادی را حل نمی‌کند؛ فقط باید ابتدا کیفیت و امنیت لایه‌های زیرین اصلاح شود.

## MCP چه مزیتی برای سازمان دارد؟

### کاهش اتصال‌های اختصاصی

تیم‌ها می‌توانند یک رابط استاندارد برای قابلیت‌های پرتکرار بسازند و آن را میان چند ایجنت یا محصول به اشتراک بگذارند. این کار هزینه ساخت و نگهداری اتصال‌ها را کاهش می‌دهد.

### جداسازی مدل از ابزار

وقتی قرارداد ابزار مستقل از مدل باشد، تغییر مدل یا میزبان ساده‌تر می‌شود. این استقلال کامل نیست، زیرا رفتار مدل‌ها و روش فراخوانی ابزار تفاوت دارد؛ اما وابستگی معماری کمتر می‌شود.

### کشف و ترکیب قابلیت‌ها

میزبان می‌تواند فهرست ابزارهای مجاز را دریافت کند و چند سرور تخصصی را کنار هم قرار دهد. یک ایجنت تحلیل ممکن است هم‌زمان به انبار داده، اسناد و سرویس نمودار متصل شود.

### نقطه کنترل روشن

لایه MCP محل مناسبی برای فیلتر ابزارها، محدودکردن ورودی، ثبت فراخوانی، اعمال نرخ، زمان‌سنجی و تأیید عملیات حساس است. البته این کنترل‌ها باید واقعاً پیاده‌سازی شوند و صرف استفاده از پروتکل آن‌ها را ایجاد نمی‌کند.

### استفاده مجدد در مقیاس سازمان

به‌جای آنکه هر تیم نسخه‌ای متفاوت از «ابزار جست‌وجوی مشتری» بسازد، یک قابلیت دارای مالک، قرارداد، نسخه و سطح خدمت مشخص ارائه می‌شود. این رویکرد از شکل‌گیری Shadow MCP و سرورهای ناشناس جلوگیری می‌کند.

## مهم‌ترین ریسک‌های امنیتی MCP

اتصال ایجنت به ابزار، سطح حمله را افزایش می‌دهد؛ زیرا خروجی مدل می‌تواند به یک اقدام واقعی تبدیل شود. راهنمای امنیت MCP در OWASP چند تهدید مهم را برجسته می‌کند.

### Tool Poisoning

توضیح یا خروجی یک ابزار آلوده می‌تواند دستور پنهانی داشته باشد و مدل را به رفتار دیگری سوق دهد. تعریف ابزار و محتوای برگشتی باید مانند ورودی غیرقابل اعتماد بررسی شود.

### مجوز بیش‌ازحد

اتصالی که برای خواندن تقویم ساخته شده نباید امکان حذف رویداد یا دسترسی کامل به صندوق پستی را داشته باشد. اعتبارنامه‌های محدود و مجوزهای کمینه، اثر خطا یا نفوذ را کاهش می‌دهند.

### Confused Deputy

اگر سرور با دسترسی گسترده خود عملی را برای کاربر کم‌اختیار انجام دهد، به «نماینده سردرگم» تبدیل می‌شود. مجوز باید برای هر کاربر و هر درخواست بررسی شود، نه فقط هنگام اتصال اولیه سرور.

### نشت داده میان ابزارها

یک سند آلوده ممکن است ایجنت را ترغیب کند اطلاعات سیستم دیگر را در یک فراخوانی ظاهراً عادی ارسال کند. جداسازی سرورها، محدودکردن داده ورودی ابزار و کنترل خروجی برای کاهش این خطر ضروری است. این تهدید با [Prompt Injection در ایجنت‌های هوش مصنوعی](/blog/ai-agent-prompt-injection-security) ارتباط مستقیم دارد.

### سرور و بسته غیرقابل اعتماد

نصب یک سرور آماده از مخزن عمومی شبیه افزودن یک وابستگی نرم‌افزاری دارای دسترسی است. منشأ کد، مالک، نسخه، امضا، وابستگی‌ها و رفتار شبکه باید بررسی شوند. «محبوب بودن» به‌تنهایی معیار اعتماد نیست.

## چک‌لیست استقرار امن MCP

OpenAI توصیه می‌کند فقط به سرورهای مورد اعتماد متصل شوید، از اعتبارنامه کم‌اختیار استفاده کنید، توکن را در URL قرار ندهید و برای عملیات حساس تأیید بخواهید. Microsoft نیز در راهنمای امنیت Azure MCP بر اعتبارسنجی issuer، audience و expiry توکن، RBAC کمینه و هویت‌های کوتاه‌عمر تأکید می‌کند.

برای محیط سازمانی این کنترل‌ها را حداقل در نظر بگیرید:

1. **فهرست مجاز سرورها:** فقط سرورهای ثبت‌شده و دارای مالک سرویس قابل اتصال باشند.
2. **فیلتر ابزار:** هر ایجنت فقط Tools لازم برای مأموریت خود را ببیند.
3. **مجوز کمینه:** دسترسی خواندن و نوشتن جدا و تا سطح کاربر، منبع و عملیات محدود شود.
4. **تأیید انسانی:** ارسال پیام، حذف، پرداخت، تغییر مجوز و اقدامات برگشت‌ناپذیر بدون تأیید اجرا نشوند.
5. **اعتبارسنجی ورودی:** نوع، طول، دامنه و الگوی پارامترهای ابزار قبل از اجرا کنترل شوند.
6. **پاک‌سازی خروجی:** نتیجه ابزار پیش از ورود به context مدل از نظر داده حساس و محتوای خصمانه بررسی شود.
7. **مدیریت امن توکن:** توکن در URL، prompt، log یا کد ذخیره نشود؛ از secret manager و توکن کوتاه‌عمر استفاده شود.
8. **ثبت و ردیابی:** هویت کاربر، نسخه سرور، ابزار، پارامترهای غیرحساس، نتیجه و تصمیم تأیید ثبت شوند.
9. **محدودیت نرخ و زمان:** برای جلوگیری از حلقه، هزینه غیرمنتظره و سوءاستفاده، سقف فراخوانی و timeout تعریف شود.
10. **Kill switch:** امکان قطع سریع یک ابزار، سرور یا اعتبارنامه بدون خاموش‌کردن کل سامانه وجود داشته باشد.

برای سنجش این کنترل‌ها پیش از انتشار، از چارچوب [Evals و KPIهای ایجنت سازمانی](/blog/ai-agent-evaluation-enterprise-kpis) استفاده کنید.

## معماری پیشنهادی MCP برای محیط Production

یک نمونه آزمایشی می‌تواند مستقیماً به یک سرور محلی متصل شود؛ اما معماری Production بهتر است لایه‌های زیر را جدا کند:

### درگاه یا Gateway

همه اتصال‌های راه دور از یک مسیر کنترل‌شده عبور کنند تا احراز هویت، نرخ، فهرست مجاز، نسخه و گزارش ممیزی یکپارچه شوند.

### Registry داخلی

برای هر سرور، مالک، هدف، ابزارها، سطح داده، نسخه، وضعیت امنیتی، وابستگی‌ها و تاریخ بازبینی ثبت شود. Registry مانع رشد اتصال‌های ناشناس می‌شود.

### Policy Engine

تصمیم دسترسی فقط در prompt نوشته نشود. یک لایه قطعی باید بر اساس کاربر، نقش، ابزار، منبع داده، سطح ریسک و محیط اجرا اجازه بدهد یا درخواست تأیید کند.

### محیط اجرای ایزوله

سرورهای محلی یا ابزارهایی که کد و فایل اجرا می‌کنند باید در sandbox با دسترسی فایل و شبکه محدود باشند. هر سرور نباید کل حافظه، فایل‌ها یا متغیرهای محیطی میزبان را ببیند.

### Observability

برای هر فراخوانی یک شناسه trace ایجاد کنید تا بتوان مسیر «درخواست کاربر → تصمیم ایجنت → ابزار → نتیجه» را دنبال کرد. این داده برای امنیت، ارزیابی کیفیت و کنترل هزینه لازم است.

نسخه ۲۰۲۶-۰۷-۲۸ پروتکل MCP، هسته بدون session و قابلیت‌های مسیریابی و cache را گسترش داده است؛ در نتیجه تیم‌ها باید نسخه پروتکل و SDK را صریح مدیریت کنند و تغییرات breaking را بدون آزمون وارد Production نکنند.

## از کدام فرایند شروع کنیم؟

بهترین نقطه شروع، فرایندی پرتکرار و قابل اندازه‌گیری با ریسک محدود است. مثال‌ها:

• جست‌وجوی دانش سازمانی با دسترسی فقط‌خواندنی؛

• خلاصه‌سازی وضعیت پروژه از چند سیستم؛

• آماده‌سازی پیش‌نویس گزارش مدیریتی؛

• طبقه‌بندی و پیشنهاد مسیر برای تیکت‌ها؛

• خواندن داده‌های عملیاتی و توضیح مغایرت‌ها.

در فاز اول از انتقال وجه، حذف داده، ارسال خودکار پیام بیرونی یا تغییر مجوز شروع نکنید. ابتدا قابلیت اتکا و کنترل انسانی را در یک دامنه محدود اثبات کنید.

## نقشه راه ۳۰ روزه پیاده‌سازی MCP

### هفته اول: انتخاب مورد استفاده و مرز دسترسی

یک فرایند مشخص انتخاب کنید. کاربران، داده‌های لازم، سیستم‌های درگیر، عملیات خواندن و نوشتن و خطاهای غیرقابل‌قبول را ثبت کنید. خروجی این هفته باید «قرارداد مأموریت ایجنت» باشد، نه کد.

### هفته دوم: ساخت سرور حداقلی

فقط دو یا سه ابزار با نام و شرح روشن ارائه کنید. طرح ورودی را محدود، خروجی را ساخت‌یافته و دسترسی را فقط‌خواندنی نگه دارید. از اتصال به نسخه آزمایشی سیستم استفاده کنید.

### هفته سوم: کنترل و ارزیابی

احراز هویت، مجوز هر کاربر، log، timeout و تأیید انسانی را اضافه کنید. سناریوهای عادی، ورودی نامعتبر، prompt injection، خرابی وابستگی و تلاش برای دسترسی خارج از محدوده را آزمایش کنید.

### هفته چهارم: پایلوت محدود

اتصال را برای گروه کوچکی از کاربران فعال کنید. نرخ موفقیت، خطای ابزار، زمان پاسخ، هزینه هر نتیجه، تعداد تأییدها و موارد ارجاع به انسان را بسنجید. ابزار نوشتنی را فقط پس از عبور از معیارهای Go/No-Go اضافه کنید.

## شاخص‌های موفقیت MCP سازمانی

موفقیت را با تعداد سرورهای نصب‌شده نسنجید. معیارهای مفیدتر عبارت‌اند از:

• درصد وظایفی که بدون اتصال اختصاصی جدید قابل اجرا شده‌اند؛

• زمان لازم برای افزودن یک قابلیت سازمانی به ایجنت؛

• نرخ موفقیت و خطای هر Tool؛

• درصد فراخوانی‌هایی که به تأیید انسانی یا توقف ایمن منجر شده‌اند؛

• تعداد سرورهای ناشناس یا خارج از Registry؛

• رخدادهای دسترسی بیش‌ازحد و میانگین زمان قطع دسترسی؛

• هزینه، latency و تعداد فراخوانی ابزار برای هر نتیجه موفق؛

• پوشش trace و قابلیت بازسازی تصمیم‌ها.

## خطاهای رایج در پروژه‌های MCP

### اتصال همه‌چیز از روز اول

ابزار بیشتر همیشه به معنی ایجنت بهتر نیست. فهرست بزرگ ابزارها انتخاب را دشوار، هزینه context را بیشتر و سطح حمله را وسیع‌تر می‌کند.

### اعتماد به شرح ابزار به‌عنوان کنترل امنیتی

عبارت «این ابزار را فقط برای مدیران استفاده کن» در prompt مجوز ایجاد نمی‌کند. کنترل باید در کد و زیرساخت اجرا شود.

### استفاده مشترک از یک حساب قدرتمند

وقتی همه درخواست‌ها با یک حساب سرویس پرقدرت اجرا شوند، انتساب عمل به کاربر و محدودکردن دسترسی دشوار می‌شود.

### نبود مالک و نسخه

سروری که مالک، SLA و چرخه نسخه ندارد، بعد از تغییر سیستم زیرین به منبع خطا تبدیل می‌شود. قرارداد ابزار را مانند API رسمی مدیریت کنید.

### نادیده‌گرفتن خروجی ابزار

داده‌ای که از یک فایل، وب‌سایت یا سرویس برمی‌گردد می‌تواند اشتباه، حساس یا خصمانه باشد. خروجی Tool ورودی قابل اعتماد نیست.

## پرسش‌های متداول

### آیا MCP فقط برای برنامه‌نویسان است؟

پیاده‌سازی آن فنی است، اما تصمیم‌های اصلی درباره مالکیت داده، سطح دسترسی، تأیید انسانی و KPI به مدیران کسب‌وکار، امنیت و محصول مربوط می‌شود.

### آیا MCP جایگزین RAG می‌شود؟

خیر. RAG روشی برای بازیابی اطلاعات مرتبط و افزودن آن به context مدل است. MCP می‌تواند دسترسی به منبع جست‌وجو یا ابزار RAG را استاندارد کند، اما خود آن موتور بازیابی نیست.

### تفاوت سرور محلی و راه دور MCP چیست؟

سرور محلی معمولاً کنار میزبان و از طریق فرایند محلی اجرا می‌شود؛ سرور راه دور از شبکه و HTTP در دسترس است. راه دور برای اشتراک سازمانی مناسب‌تر است، اما احراز هویت، TLS، محدودیت شبکه و پایش جدی‌تری نیاز دارد.

### آیا می‌توان به هر سرور عمومی MCP اعتماد کرد؟

خیر. سرور به داده و ابزار دسترسی پیدا می‌کند و ممکن است زنجیره تأمین یا رفتار شبکه پرریسکی داشته باشد. فقط سرور بررسی‌شده با نسخه مشخص و مجوز کمینه را وارد محیط سازمان کنید.

### برای شروع چند Tool کافی است؟

دو یا سه ابزار محدود و پرکاربرد معمولاً برای پایلوت بهتر از یک کاتالوگ بزرگ است. ابتدا نرخ موفقیت و کنترل دسترسی را اثبات و سپس دامنه را گسترش دهید.

## جمع‌بندی

MCP یک زبان مشترک برای اتصال برنامه‌های هوش مصنوعی به داده و ابزار ایجاد می‌کند. این استاندارد می‌تواند هزینه اتصال‌های اختصاصی را کاهش دهد، استفاده مجدد را بیشتر کند و نقطه کنترل روشن‌تری برای ایجنت‌های سازمانی بسازد. اما پروتکل به‌تنهایی امنیت، کیفیت یا حاکمیت را تضمین نمی‌کند.

پیاده‌سازی موفق با یک مورد استفاده محدود، ابزارهای کم، مجوز حداقلی، تأیید عملیات حساس، Registry داخلی، trace کامل و Eval مستمر آغاز می‌شود. اگر ابتدا می‌خواهید اجزای پایه را بشناسید، [راهنمای ایجنت هوش مصنوعی سازمانی](/blog/ai-agent-enterprise-guide) را بخوانید؛ و اگر در حال طراحی نقش‌ها و مالکیت هستید، مقاله [ساختار سازمانی لوزی‌شکل](/blog/diamond-shaped-agentic-organization) مکمل این راهنماست.

تیم nexation می‌تواند در طراحی معماری ایجنت، انتخاب نقطه شروع، ساخت ابزارهای سازمانی و تعریف کنترل‌های اندازه‌پذیر برای استقرار Production همراه شما باشد.
